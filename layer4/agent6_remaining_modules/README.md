
# FlashGuard – Agent 6: Execution Orchestrator

## Overview

Agent 6 is the **final execution layer** of the FlashGuard fraud detection pipeline.

All previous agents analyze a transaction and produce signals or recommendations. Agent 6 is responsible for **executing the final decision** in a safe, reliable, and auditable manner.

Typical responsibilities include:

- Validating incoming execution requests
- Preventing duplicate execution (Idempotency)
- Selecting an execution policy
- Creating an execution plan
- Executing actions
- Writing immutable audit logs
- Publishing events
- Recording metrics

# Module Responsibilities

## models.py

Contains all shared models used throughout the project.

Includes:

- Verdict
- ActionType
- ExecutionState
- ActionStatus
- EventType
- Policy
- ExecutionRequest
- ExecutionPlan
- Action
- ActionResult
- ExecutionResult
- AuditEvent
- ExecutionMetrics

---

## validator.py

Validates incoming execution requests.

Checks include:

- Transaction ID
- Required fields
- Request format

Rejects malformed requests before execution begins.

---

## idempotency.py

Ensures exactly-once execution.

Responsibilities:

- Generate execution key
- Detect duplicate requests
- Return cached execution result
- Prevent duplicate card locks

---

## distributed_lock.py

Prevents multiple executors from processing the same transaction simultaneously.

Useful in multi-instance deployments.

---

## policy_engine.py

Maps business decisions into executable actions.

Example:

BLOCK →

- Lock Card
- Freeze Transaction
- Create Case
- Notify FIU
- Write Audit
- Publish Event

ALLOW →

- Write Audit
- Publish Event
- Update Metrics

The executor never contains business rules.

---

## planner.py

Converts actions into an ordered ExecutionPlan.

Responsibilities:

- Sort actions
- Assign execution order
- Create execution ID

---

## retry.py

Retries transient failures.

Features:

- Retry manager
- Retry metadata
- Retry attempts

---

## circuit_breaker.py

Protects downstream services.

Implements:

- CLOSED
- OPEN
- HALF-OPEN

Prevents cascading failures.

---

## action_runner.py

Executes actions generated by the planner.

Examples:

- Lock card
- Freeze transaction
- Notify customer
- Write audit
- Publish event

Returns ActionResult objects.

---

## event_bus.py

Simple publish-subscribe messaging layer.

Responsibilities:

- Publish events
- Subscribe handlers
- Topic routing

Designed so it can later be replaced with Kafka or RabbitMQ.

---

## audit.py

Stores immutable audit records.

Every execution generates an audit event containing:

- Execution ID
- Transaction ID
- Trace ID
- Policy
- Latency
- Execution state

---

## metrics.py

Collects runtime metrics.

Tracks:

- Executions
- Successes
- Failures
- Cache hits
- Retries
- Latency statistics

---

## executor.py

Core orchestration module.

Pipeline:

1. Validate request
2. Check idempotency
3. Acquire distributed lock
4. Build execution plan
5. Execute actions
6. Cache result
7. Write audit
8. Publish event
9. Release lock

---

## container.py

Central dependency registry.

Creates service instances and wires them together.

---

## main.py

CLI entry point.

Creates an ExecutionRequest and executes Agent 6.
